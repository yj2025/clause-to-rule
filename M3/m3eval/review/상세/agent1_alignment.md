# Agent 1 — 의사결정표 ↔ 프롬프트 정합성 감사 (system_v0.3)

감사 대상: `in/system_v0.3.txt` (rule 1~16, 출력 스키마)
대조 자료: `in/table_dump.txt` (회의요약 / 기획_배치결정표 / 최초입력_추천안 / 참고근거)

표기: [확인] = 두 파일 텍스트로 직접 확인한 사실, [추정] = 파이프라인 동작이나 팀 의도에 대한 추정.

## 0. 먼저 짚을 사실 (감사 전제 보정)

1. [확인] "프롬프트 IN" 항목은 **23개**다. 열 위치를 파싱해 검증했다.
2. [확인] **기본금리·기본이율·적용이율은 '제외'가 아니라 '프롬프트 IN'**이다. 행 32를 보면 `… | 보류 | 생존 | 프롬프트 IN |`이다. 감사 지시문의 전제("기본금리는 제외")는 표와 다르다. '제외'인 것은 **우대금리·우대이율 조건**(행 33)과 **계약·가입·저축기간**(행 28)이다.
3. [확인] **서비스 상태는 '프롬프트 IN'이 아니라 '제외'**다. 팀 결정은 보류, 메모는 "죽어"다. 그런데 회의요약에는 "상품고유 제한/특수상태 → 중대한 경우만 최초출력 (혁신금융서비스 종료처럼)"이라고 적혀 있다. 표 안에서 이미 충돌이 있다.
4. [확인] IN 23개를 **팀 최종 결정** 기준으로 나누면 다음과 같다.
   - 확정 7: 가입대상, 금리구조, 만기앞당김, 중도해지, 계약해지 방법, 세제, 수수료
   - 보류 4: 기본금리, 부가·제휴혜택, 상품·계좌 전환, 정부지원금
   - 원본 확인 필요 5: 가입신청 절차, 가입제한, 계좌수·중복가입, 거래제한, 양도·질권
   - '확인 필요' 1: 가입금액. 이 값은 열에 정의된 enum(확정/보류/제외/원본 확인 필요) 밖에 있다.
   - **팀 결정 '제외'인데 프롬프트 IN 6**: 이벤트·쿠폰, **최고·최종 공시금리**, 자동재예치, 자동해지, 관련대출, 명의변경
   → IN 항목 중 **확정은 7/23(30%)**뿐이다. "팀 최종 결정"·"팀 메모(생존/죽어)"·"프롬프트 IN/제외" 세 신호가 서로 어긋나는 행이 많다. 표만 보고 프롬프트를 고정하기에는 아직 이르다.
5. [확인] 프롬프트는 정보 항목명을 **하나도** 직접 다루지 않는다. 예시로만 세 번 등장한다(rule 12 "최고금리", rule 15 "우대금리", rule 5 "고시 금리"). 따라서 항목별 표현 규칙은 모두 ① 일반 규칙(rule 1~16)으로 커버되거나 ② 입력(must_include_fact_ids · dependencies · section_order)에 위임된 것으로 봐야 한다. 그런데 **프롬프트 어디에도 "항목별 우선순위·노출 여부는 상위 단계가 must_include/section_order로 결정한다"는 위임 선언이 없다.**

## 2. 구조적 지적 (항목 공통)

### 2-A. 제한·불이익형 Fact의 state 극성이 정의돼 있지 않다 [높음]
- [확인] rule 10의 문구 템플릿은 SATISFIED → "적용됩니다", UNSATISFIED → "적용되지 않습니다 + 어떤 조건이 모자란지"로, **혜택형**에 맞춰져 있다.
- 관련 행: 가입제한·제외조건, 계좌수·중복가입 제한, 거래제한, 중도해지(불이익)
- [추정] 2-2 판정 코드가 "가입제한 조건에 해당함"을 SATISFIED로 낸다면, 모델은 "입력하신 내용 기준으로 적용됩니다"라고 쓴다. 이 문장은 "가입 제한이 적용된다"로도, "가입 가능하다"로도 읽힌다. 반대로 UNSATISFIED + "어떤 조건이 모자란지"는 제한 조건에 대해 의미가 뒤집힌다("모자라서 제한에 안 걸린다"?).
- 수정 제안 (rule 10 아래에 추가):
  > `candidate_facts` 의 `key` 가 제한·불이익 유형(가입제한, 중복가입 제한, 거래제한, 중도해지 등)이면 state 는 "이 제한(불이익)이 고객에게 해당하는지"를 뜻한다. SATISFIED 는 "입력하신 내용 기준으로 이 제한에 해당합니다", UNSATISFIED 는 "입력하신 내용 기준으로 이 제한에 해당하지 않습니다"로 쓴다. "가입 가능/불가", "추천"이라는 말은 쓰지 않는다.
  - 더 결정론적인 방법은 2-4 단계가 `fact_type: benefit|restriction|info` 필드를 넘기는 것이다.

### 2-B. 조건이 있는데 judgment가 없는 Fact를 "INFO"로 단정할 수 있다 [높음]
- [확인] 출력 규칙: "state 가 없는 일반 정보 문장(금리 안내 등)은 "INFO"로 적는다."
- 관련 행: 최고·최종 공시금리("'조건 충족 시'와 함께"), 이벤트·쿠폰("대상 확인 전 확정표현 금지"), 우대금리(제외지만 표현 방침 "사용자 적용 여부는 미확정으로 표시"), 회의요약 "우대금리 표현 → 미확정 조건과 분리"
- 최초 출력 시점에는 사용자 정보가 거의 없다. 그래서 최고금리 Fact에 judgment_result가 없을 가능성이 높다 [추정]. 그러면 "최고 연 X.XX%(세전, 2026-10-13 기준)"가 INFO로 나가고, rule 6이 요구하는 조건 병기만으로는 "이 금리가 고객 금리가 아니다"라는 미확정성이 드러나지 않는다.
- 수정 제안 (rule 10에 항목 추가):
  > - (판정 없음) `condition` 이 있는 Fact 에 judgment_results 가 없으면 state 를 "INFO" 로 쓰되, 문장에 반드시 "조건을 충족하는 경우"를 넣고 "고객에게 적용되는지는 아직 확인되지 않았습니다"를 덧붙인다. 최고금리 · 우대금리 · 이벤트 금리를 고객이 받는 금리처럼 쓰지 않는다. 최고금리는 기본금리 없이 단독으로 쓰지 않는다.

### 2-C. 최초 출력 / 상세보기 층위가 프롬프트에 없다 [중간]
- [확인] 표는 "최초 출력 추천"(기본/조건부/상세 중심)과 "상세보기" 열을 따로 둔다. 프롬프트 출력은 `sections` 하나뿐이다.
- IN 항목 중 "상세 중심"인 행(계약해지 방법, 관련대출, 명의변경, 양도·질권)은 "조건이 크면 최초 출력"이라는 판단이 필요하다. 프롬프트는 그 판단 기준도, 상세로 미룰 출력 칸도 주지 않는다.
- 수정 제안: 둘 중 하나를 고른다. (a) 상위 단계가 최초 출력용 facts만 넘기고, 프롬프트에 "candidate_facts 는 이미 이번 화면에 넣을 정보로 걸러져 있다"라고 명시한다. (b) 출력에 `"detail_fact_ids": [...]`를 추가하고 "상세 중심 정보는 문장으로 쓰지 말고 detail_fact_ids 에만 넣는다"라는 규칙을 둔다. 멘토 지적(소형 모델, 정보량 축소, 결정론)을 고려하면 **(a)가 적합하다.**

### 2-D. 배치·우선순위 위임이 명시돼 있지 않다 [높음]
- [확인] 입력 설명: "must_include_fact_ids: 반드시 반영할 fact_id", "section_order: 섹션 순서". 무엇을 기준으로 채워지는지는 적혀 있지 않다. 섹션 **안**의 순서는 rule 14 "고객에게 중요한 것부터"라는 모델 재량에 맡겨져 있다.
- 표의 배치 요구(가입제한 → 혜택보다 먼저, 중도해지 → 핵심 불이익, 자동재예치·자동전환 → 앞쪽, 변동금리 → 앞쪽 위험, 거래제한 → 심각도별)는 모두 **섹션 내 순서 또는 포함 여부**에 관한 것이다. 이 부분이 Qwen2.5-7B의 재량에 남아 있다.
- 수정 제안 (rule 14 교체):
  > 14. section_order 순서로 섹션을 만든다. 각 섹션 안에서는 (1) 가입을 막거나 제한하는 조건, (2) 손해·불이익(중도해지이율, 자동 재예치·자동 전환·자동 해지, 변동 금리, 거래 제한), (3) 금리·혜택과 그 조건, (4) 그 밖의 정보 순으로 쓴다. 입력에 `priority` 가 있으면 그 순서를 따른다. 무엇을 넣을지는 must_include_fact_ids 와 candidate_facts 가 이미 정한 것이며, 너는 그 안에서 빼지 않는다.
  - 결정론을 높이려면 2-4 단계가 각 fact에 `priority`(정수)를 붙여 주고, 프롬프트는 "priority 오름차순"만 지키게 하는 편이 낫다.

### 2-E. rule 13이 불이익을 탈락시키는 방향으로 작동할 수 있다 [높음]
- [확인] rule 13: "purpose 와 고객 상황에 관련된 Fact 를 먼저 고른다. 판단에 도움이 안 되는 Fact 는 넣지 않는다 — 단 must_include 는 예외."
- 감독규정 제13조(참고근거 시트: "계약판단·권익보호에 중요한 특징·불이익의 앞부분 요약")와 회의요약("정기예금/적금의 중도해지 정보 → 최초 요약에 포함")은 **purpose와 무관하게** 불이익을 앞에 둘 것을 요구한다. purpose="금리가 얼마인지"이면 7B 모델이 중도해지·자동재예치를 "판단에 도움 안 됨"으로 볼 위험이 있다.
- 수정 제안 (rule 13에 단서 추가):
  > 단, 제한 · 불이익 · 자동 처리(자동 재예치 · 자동 전환 · 자동 해지)에 관한 Fact 는 purpose 와 관련이 없어도 빼지 않는다.

### 2-F. product_type 입력이 없다 [중간]
- [확인] 상품유형·예금과목은 '제외'(프론트 표시)다. 그런데 "상품군별 기본" 항목(중도해지 → 정기예금·적금이면 핵심 불이익)은 상품군 분기를 전제로 한다. 프롬프트 입력에는 product만 있고 유형이 없다.
- 프론트 표시와 별개로 **모델 입력**에는 필요하다. 넣지 않을 거라면 must_include가 상품군별로 채워진다는 것을 위임 문구로 명시해야 한다.
- 수정 제안: `- product_type: 거치식 | 적립식 | 입출금식 (표시용 아님 · 순서와 필수 항목 판단용)`

## 3. "제외" 항목 중복 출력 위험

| 제외 항목 | 중복 경로 | 위험 | 근거 |
|---|---|---|---|
| **우대금리·우대이율 조건** | rule 12 예시 "최고금리를 말하면 그 금리의 **조건**·한도·기간도"와 rule 6 "금리는 적용 조건과 한 문장"을 함께 적용하면, 최고금리(IN)를 쓰는 순간 우대조건 목록이 문장에 들어간다 | **높음** | 표 행 37 "기본금리/조건과 묶어"(병기 요구)와 행 33 "프론트가 이미 보여 줌"(제외)이 **표 안에서 이미 긴장 관계**다. 프롬프트가 한쪽(병기)만 강제한다 |
| 계약·가입·저축기간 | 같은 예시의 "**기간**" | 중간 | 한 단어 수준이라 실해는 작지만 중복이다 |
| 회차·월·연·총 납입한도 | 같은 예시의 "**한도**". 우대금리 한도인지 납입한도인지 모호하다 | 중간 | 7B 모델이 납입한도 Fact를 가져다 붙일 수 있다(rule 3 위반 위험도 있음) |
| 기본금리 | (IN이므로 중복 아님) | — | 감사 지시문 전제 보정, §0-2 |
| 예금자보호 | rule 4가 "보장"을 금지할 뿐 예금자보호 Fact가 들어오면 쓰게 된다 | 낮음 | 회의요약 "첫 화면 고정 한 줄", 표 '제외'(프론트 고정)이 정합하다. 상위 단계가 Fact를 넘기지 않으면 문제없다 |
| 상품특징·성격 | 없음(입력되지 않으면 쓰지 않음) | 낮음 | |

**핵심 충돌**: rule 12의 예시는 감독규정 제13조(혜택+조건 병기)에 충실하다. 하지만 "제외 = 프론트가 이미 보여 줌" 방침과 정면으로 겹친다. 프롬프트에는 "화면에 이미 있는 정보" 개념이 없어 모델이 조정할 수 없다. [추정] 상위 단계가 우대조건 Fact를 candidate_facts에서 빼면, dependencies가 존재하지 않는 fact_id를 가리켜 `omitted_must_include` 처리 혹은 환각 위험이 생긴다.

수정 제안
1. 입력에 `shown_on_screen: [fact_id…]`(프론트에 이미 표시된 Fact)를 추가하고, 규칙을 둔다.
   > shown_on_screen 의 Fact 는 다시 풀어 쓰지 않는다. dependencies 때문에 함께 말해야 하면 "화면의 우대조건을 충족하는 경우"처럼 짧게 가리키기만 하고, fact_id 는 적는다.
2. rule 12 예시를 표 행 37에 맞게 바꾼다.
   > 예: 최고금리를 말하면 기본금리와 "우대조건 충족 시"라는 전제를 같은 문장에 쓴다.

   "한도·기간"은 dependencies 입력이 실제로 지정할 때만 쓴다.

## 5. '추가 질문 추천=예' ↔ INFO_MISSING / questions_for_user

[확인] 추가 질문 '예'는 8개(회의요약 수치 8과 일치)다. 가입대상, 가입제한, 계좌수·중복가입, **우대금리(제외)**, 이벤트·쿠폰, **연결계좌(제외)**, 부가·제휴혜택, 정부지원금. 이 중 IN은 6개다.

|---|---|---|---|
| **우대금리는 '추가 질문=예'인데 프롬프트 '제외'**다. 이 서비스의 대표 개인화 축(행 33 "질문 후 실제 적용 가능분을 개인화하는 흐름을 **강하게 추천**")이 프롬프트 질문 흐름에서 빠질 수 있다 | 높음 | 행 33: `… | 예 | 사용자 정보에 따라 우대금리 적용 여부가 달라질 때 | … | 제외 | 생존 | 제외` | '제외'의 뜻을 "조건 **목록 표시**는 프론트, **적용 판정 문장과 질문**은 프롬프트"로 팀이 분리 확정한다. 프롬프트에는 §3의 shown_on_screen 규칙을 넣어 판정 문장만 쓰게 한다 |

| 질문 중복 제거·상한 없음 | 중간 | 출력 `questions_for_user: [...]` | 여러 Fact가 같은 field(예: 나이)를 요구하면 같은 질문이 여러 번 나온다. 다음을 추가한다. "같은 field 는 한 번만 묻는다. 질문은 missing_fields 에 있는 것만 만들고, 그 밖의 개인정보는 묻지 않는다." (개인정보보호법 제16조 최소수집, 최초입력_추천안 원칙) |
| 질문 ↔ Fact 연결 없음 | 낮음 | 출력이 문자열 배열뿐 | `{"field":..., "question":..., "fact_ids":[...]}`로 구조화하면 일치율 테스트·재판정 루프가 쉬워진다 |

## 6. 팀 결정 '보류' / '원본 확인 필요' 항목의 확정 취급

| 지적 | 심각도 | 근거 |
|---|---|---|
| rule 12가 **팀 결정='제외'인 최고·최종 공시금리**를 규칙 예시로 고정했다. 행 37은 프롬프트 IN이지만 팀 최종 결정 열은 '제외'다 | 중간 | 표 신호 3개가 충돌하는 행을 프롬프트가 확정 규칙으로 박아 넣었다. 예시를 일반형으로 바꾸거나("A 혜택을 말하면 B 조건도") 팀 확정 후 유지한다 |
| rule 15 예시 "우대금리"(팀='제외'), rule 5 "고시 금리"(기본금리=보류) | 낮음 | 용어 예시라 실해는 작다 |
| IN 23개 중 16개가 미확정(보류 4 · 원본 확인 필요 5 · 확인 필요 1 · 팀 '제외' 6) | 높음(프로세스) | 프롬프트 자체는 항목을 몰라 "확정 취급"하지 않는다. 그러나 **일치율 테스트 정답셋을 이 표로 만들면 미확정 항목이 정답으로 굳는다.** 테스트 셋은 '확정 7개' 항목부터 만들 것을 권한다 |
| BANK_CONFIRM_NEEDED ≠ "원본 확인 필요" | 낮음 | 팀 결정의 "원본 확인 필요"는 **팀이 약관 원문을 확인할 일**이고, BANK_CONFIRM_NEEDED는 **고객이 은행에 확인할 일**이다. 2-2 단계가 둘을 섞어 원본 미확인 항목을 BANK_CONFIRM_NEEDED로 흘리면 고객에게 "은행 확인 필요"가 과다 노출된다 [추정]. 원본 미확인 Fact는 candidate_facts에 넣지 않는 것이 맞다 |
| '확인 필요'(가입금액) 값은 enum 밖이다 | 낮음 | 표 정리 이슈 |

**'추천 가능/불가' 방침과의 정합 [높음]**
- [확인] 프롬프트에는 "추천"이라는 단어 자체가 금지어로 나오지 않는다.
- 표의 표현 방식 열이 "적합 여부를 표시"(행 23), "가입 가능/불가 판정"(행 18, 20, 21), "유동성 적합성"(행 39, 40)처럼 **판정 내부 용어**를 쓴다. [추정] 2-4 단계의 `reason` 문자열에 "가입 가능"·"적합"이 실리면, 모델은 rule 1에 따라 그 근거를 그대로 옮긴다.
- 수정 제안 (rule 16 교체):
  > 16. 상품을 권하거나 다른 상품과 비교하지 않는다. "추천", "적합합니다", "유리합니다", "가입하세요", "좋은 선택" 같은 말과 수익 · 혜택을 보장하는 말을 쓰지 않는다. 가입 자격은 "가입 가능/불가"가 아니라 "입력하신 내용 기준으로 가입 대상 조건에 해당합니다 / 해당하지 않습니다"로 쓴다. judgment_results 의 reason 에 이런 말이 있어도 옮기지 않는다.
