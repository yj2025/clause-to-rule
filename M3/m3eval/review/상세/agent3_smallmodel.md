# 평가 3 — Qwen2.5-7B-Instruct 실행 관점 점검 (system_v0.3)

평가자 관점: 이 프롬프트를 Tesla V100 32GB · fp16 · transformers(vLLM 없음)로 직접 돌릴 엔지니어.
표기: **[확인]** = 프롬프트·의사결정표 텍스트에서 직접 확인한 사실 / **[추정]** = 소형 모델 경험칙·문서 기억에 근거한 판단(실측 필요).

---

## 0. 한 줄 결론

v0.3은 "큰 모델이면 지킬 수 있는" 프롬프트다. 7B에게는 **문장 쓰기 + 근거 ID 달기 + 상태 라벨 복사 + 집합 계산 + 의존 쌍 검사 + 자기 누락 보고 + 질문 생성 + JSON 직렬화**를 한 번의 생성에서 동시에 시키고 있다. 이 중 **문장 쓰기를 뺀 나머지는 전부 코드로 뺄 수 있다.** 멘토 원칙("판정은 코드, AI는 문장만")을 출력 단계까지 밀고 가면, 모델 출력은 "슬롯 ID + 문장" 목록으로 줄고 JSON·숫자·상태 라벨을 모델이 아예 쓰지 않게 된다. 이것이 가장 큰 개선이다.

## 1. 프롬프트 길이·밀도

### 1-1. 토큰 수 [추정]
- 실제 토크나이저 계산 시도 → 실패: 환경에 transformers 없음, huggingface.co 접속이 프록시에서 403으로 막힘(tiktoken 인코딩 파일도 차단). **아래는 추정치다.**
- 문자 구성 [확인]: 전체 2,891자 = 한글 음절 1,085 + ASCII(영문 키·JSON·공백·기호) 1,755 + 기타 51. 56줄.
- Qwen2.5 토크나이저(151k 어휘, byte-level BPE)는 한국어 음절당 대략 0.7–1.0 토큰, 영문/기호는 3–4자당 1 토큰 수준으로 추정 → **system 프롬프트 약 1,200–1,700 토큰**.
- 길이 자체는 32k 컨텍스트 대비 작다. 문제는 길이가 아니라 **밀도**다: 규칙 16개 + PA3 하위 4개, 규칙 문장 약 63개 안에 **부정형 지시가 약 20개("~지 않는다")**, 규칙 하나에 지시 3–4개가 접혀 있음(예: 규칙 1 = 근거 제한 + 문장별 fact_id 표기 + 상식 금지; 규칙 7 = 예외 유지 + 제외조건 동반 + only_in 처리 + 출처 꼬리표).
- 입력까지 합치면(아래 6절) 실제 프롬프트는 **5k–10k 토큰**이 될 수 있다 [추정]. 규칙이 맨 앞, 출력 형식이 system 끝에만 있어 입력이 길어질수록 규칙과 생성 시점 사이 거리가 멀어진다.

### 1-2. 소형 모델이 잘 못 지키는 유형별 지적

**[심각도: 높음] 규칙 1 (CF1) — 문장마다 fact_id 달기**
- 근거 [확인]: "근거로 쓴 fact_id 를 문장마다 적는다." + 출력 스키마 `"fact_ids": ["..."]`.
- 문제 [추정]: 7B는 문장을 쓰면서 동시에 "그 문장이 실제로 쓴 fact"를 역추적하는 데 약하다. 흔한 실패: ① 섹션 첫 fact_id를 모든 문장에 복사, ② 입력에 없는 ID 생성(예: `F_rate_01` → `F_rate_1`), ③ 여러 fact를 합친 문장에 하나만 기재. CF1 평가가 이 필드에 의존하면 **문장은 맞는데 ID가 틀려서 감점/오탐**이 난다.
- 수정 제안: 모델이 fact_id를 고르지 않게 한다. 코드가 "문장 슬롯"(slot_id → 사용할 fact 묶음)을 미리 정하고, 모델은 슬롯마다 문장 하나만 쓴다. fact_ids는 코드가 슬롯에서 붙인다(3절).

**[심각도: 높음] 출력 `used_fact_ids` — 집합 연산형 출력**
- 근거 [확인]: `"used_fact_ids": ["..."]` — 모든 문장 fact_ids의 합집합.
- 문제: 생성 모델에게 합집합을 시키면 누락·중복·미사용 ID 포함이 생긴다. 게다가 이 값은 **위 문장들에서 결정론적으로 계산 가능**하므로 모델이 써야 할 이유가 없다. 모델이 쓴 값과 실제 값이 다르면 어느 쪽을 믿을지도 모호해진다.
- 수정 제안: 출력 스키마에서 삭제. `used = ∪ sentence.fact_ids` 를 코드에서 계산.

**[심각도: 높음] 규칙 11 (CC1) — `omitted_must_include` 자기 보고**
- 근거 [확인]: "반영하지 못한 것이 있으면 omitted_must_include 에 이유와 함께 적는다."
- 문제 [추정]: 소형 모델은 자기 누락을 거의 보고하지 않는다(빈 배열 `[]`이 가장 그럴듯한 다음 토큰). 즉 이 필드는 실패할 때 정확히 비어 있는, 신호가 없는 필드가 된다. 금융에서 "필수 정보 누락"은 멘토가 말한 치명 오류 범주.
- 수정 제안: 삭제하고 코드로 `omitted = must_include − used` 계산 → 비어 있지 않으면 **해당 슬롯만 재생성**(최대 1–2회) 후에도 남으면 코드가 원문 fact.text를 그대로 붙이는 폴백. "이유"는 코드가 `"생성 실패(재시도 2회)"` 처럼 기록.

**[심각도: 높음] 규칙 12 (CC2) — dependencies 쌍 검사**
- 근거 [확인]: "dependencies 의 A 를 말했으면 B 도 말한다. 예: 최고금리를 말하면 그 금리의 조건 · 한도 · 기간도 말한다."
- 의사결정표 행 [확인]: `최고·최종 공시금리`(프롬프트 IN) — "최고금리는 '조건 충족 시'라는 표현과 함께 표시", 팀 메모 "마케팅식 최고금리만 단독 강조하지 않고…". 반면 `우대금리·우대이율 조건`은 "제외"(프론트에 이미 보여 줌).
- 문제: 쌍 검사는 "내가 A를 썼는가?"를 자기 출력 위에서 판단해야 하는 일 — 7B가 가장 못하는 유형. 또한 B(우대 조건)가 "제외" 항목이라 candidate_facts에 안 들어오면 **규칙 12를 지킬 수 없는 입력**이 될 수 있다 [추정: 2-4 단계 정리 방식에 따라 다름 — 확인 필요].
- 수정 제안: 프롬프트 전에 코드가 **의존 폐포(closure)** 를 계산해 A와 B를 **같은 슬롯에 묶어서** 준다("이 슬롯은 F7과 F8을 한 문장으로"). 생성 후에는 코드가 `A∈used ⇒ B∈used` 를 검사. 규칙 12 문장은 프롬프트에서 삭제 가능.

**[심각도: 중간] 규칙 10 (PA3) — state 라벨 복사 + 상태별 강도**
- 근거 [확인]: 출력 각 문장에 `"state": "SATISFIED|…|INFO"`, 하위 규칙 4개 + 56줄 "state 가 없는 일반 정보 문장(금리 안내 등)은 "INFO"로 적는다."
- 문제: ① 라벨 복사는 코드가 할 일인데 모델이 하면 틀릴 수 있다(문장이 여러 fact를 쓰고 그 state가 다르면 어떤 라벨? — 규칙에 없음 [확인]). ② "입력하신 내용 기준으로 적용됩니다" 같은 **고정 문구**를 모델이 매번 재생성하면 표현이 흔들린다(“적용될 예정입니다”, “적용 가능합니다” 등) — PA3 일치율 테스트에 직접 불리.
- 수정 제안: state는 코드가 슬롯에 부여. 상태 고정 문구는 **코드가 문장 뒤/앞에 템플릿으로 붙이거나**, 모델에게 "이 슬롯은 [적용됨] 슬롯이니 끝 문구는 붙이지 말고 조건·혜택만 쓰라"고 하고 코드가 결합. 최소한 모델 출력에서 `state` 필드는 삭제.

**[심각도: 중간] 부정형 지시 비중**
- 근거 [확인]: 규칙부 "~지 않는다/않고" 약 20회. 예: "쉬운 말로 풀어 쓰기는 하지 않는다", "같은 말을 되풀이하지 않는다", "될 것 같다는 추측을 붙이지 않는다".
- 문제 [추정]: 소형 모델은 부정 지시 속 예시 단어를 오히려 끌어 쓰는 경향(“항상”, “보장”, “모두”가 규칙 2·4·16에 직접 등장 → 프라이밍). 금지는 출력 단계 금칙어 검사로 코드가 잡는 편이 확실하다.
- 수정 제안: 긍정형으로 바꾸고 금칙어는 코드 검사로 이동. 예: 규칙 4 → "강도 표현은 Fact 원문에 있는 것만 쓴다." + 코드: `("항상","누구나","확실히","보장","무조건","반드시 받")` 이 출력에 있고 해당 fact.text에 없으면 재생성.

**[심각도: 중간] 규칙 13·14 — 선택(R1–R4)과 구성(C1–C4)을 모델에 맡김**
- 근거 [확인]: "purpose 와 고객 상황에 관련된 Fact 를 먼저 고른다. 판단에 도움이 안 되는 Fact 는 넣지 않는다".
- 의사결정표 [확인]: 프롬프트 IN 항목이 21개(가입대상·자격조건, 가입제한·제외조건, 계좌수·중복가입 제한, 신규·가입·예치금액 조건, 금리구조·연동방식, 기본금리, 이벤트·쿠폰·특별금리, 최고·최종 공시금리, 만기앞당김 지급, 자동재예치, 자동해지, 중도해지·중도해지이율, 계약해지 방법·채널, 세제·과세·비과세, 거래·이용·입출금 제한, 관련대출, 명의변경, 수수료·수수료면제, 양도·질권, 부가·제휴 혜택, 상품·계좌 전환, 정부·기업 지원금). 다수가 "조건부"(“제한이 있는 상품이면”, “불가하거나 불리한 조건이 큰 상품에서만 표시”).
- 문제: "조건부 표시" 판단을 7B가 하게 하면 매번 다른 집합이 나온다(일치율 저하). 표의 "최초 출력 추천" 열 자체가 이미 결정 규칙이다.
- 수정 제안: 선택은 코드: `must_include ∪ (purpose 태그에 매핑된 key) ∪ (state ≠ 없음인 fact)` → 상한 N개(6절). 모델에는 이미 고른 fact만 준다. 규칙 13은 "같은 내용을 두 번 쓰지 않는다" 정도만 남김.

**[심각도: 중간] 규칙 5 (FD1) — "세전 여부를 같이 적는다"인데 입력 필드가 없음**
- 근거 [확인]: 규칙 5 "고시 금리는 기준일(as_of)과 세전 여부를 같이 적는다." 그러나 candidate_facts 필드는 `{fact_id, key, text, value, unit, condition, exceptions, only_in, as_of}` — 세전/세후 필드가 없다.
- 문제: 모델이 text에서 찾거나, 없으면 "세전"을 **지어낼** 가능성(CF1 위반을 규칙 5가 유도). 7B는 "적으라"는 지시가 있으면 근거가 없어도 채우는 경향이 강하다 [추정].
- 수정 제안: 입력에 `tax_basis: "세전"|"세후"|null` 추가, 그리고 금리 표시 문자열은 코드가 렌더링(3-5절). null이면 코드가 "(세전·세후 여부 원문 미기재)"를 쓰거나 해당 꼬리표 생략 — 팀이 정할 누락값 규칙.

## 2. JSON 출력 안정성

**[심각도: 높음] 출력 형식 — 2단 중첩 배열 + 한국어 문장 내 따옴표**
- 근거 [확인]: `sections[] → sentences[] → {text, fact_ids[], state}` (배열 3단: sections/sentences/fact_ids). 규칙 문장 자체가 "입력하신 내용 기준으로 적용됩니다"처럼 **큰따옴표로 문구를 보여 줌** → 모델이 출력 text 안에서도 큰따옴표를 쓰기 쉬움 → 이스케이프 누락 시 JSON 파싱 실패 [추정, 소형 모델에서 자주 보는 실패].
- 기타 Qwen2.5 경향 [추정]: "JSON 하나만, 다른 글 없이"를 줘도 ```` ```json ```` 코드펜스로 감싸거나, 끝에 한국어 설명 한 줄을 붙이는 경우가 있음. 긴 출력에서 max_new_tokens에 걸려 **닫는 괄호 없이 잘리는** 경우가 가장 치명적(전체 파싱 실패).
- 수정 제안(우선순위 순):
  1. **모델 출력에서 JSON을 없앤다.** 슬롯별 줄 형식으로: `[S2] 문장` — 정규식 `^\[(S\d+)\]\s*(.+)$` 로 파싱. 따옴표·이스케이프·중첩 문제 자체가 사라지고, 잘려도 앞 슬롯들은 살릴 수 있다. 최종 JSON은 코드가 조립.
  2. JSON을 유지해야 한다면 constrained decoding(아래) + 스키마를 평평하게: `{"sentences":[{"slot":"S1","text":"..."}]}` (1단 배열). 섹션 제목·순서는 코드가 slot→section 매핑으로 처리.
  3. 프롬프트 예시 문구의 큰따옴표를 「」로 바꾸고 "문장 안에 큰따옴표(\")를 쓰지 않는다"를 출력 규칙에 1줄 추가. 사후: 코드펜스 제거 → `json.loads` → 실패 시 `json_repair` 류 복구 → 그래도 실패 시 재시도.

**[심각도: 높음] 디코딩 설정 — Qwen 기본 generation_config가 샘플링**
- [추정, 공식 저장소 generation_config.json 기억 기반 — 확인 권장]: Qwen2.5-7B-Instruct 기본값은 `do_sample=True, temperature=0.7, top_p=0.8, top_k=20, repetition_penalty=1.05`. `model.generate()`를 인자 없이 부르면 **이 값으로 샘플링**된다 → 같은 입력에 매번 다른 출력, 일치율 테스트가 의미를 잃음.
- 권장:
  - `do_sample=False`(greedy) 명시. 필요하면 `temperature`/`top_p`/`top_k`를 None으로 덮어 경고 제거.
  - `repetition_penalty=1.0` (1.05도 반복 등장하는 fact_id·JSON 키·"입력하신 내용 기준" 같은 정당한 반복을 깎는다. 반복 문제는 `no_repeat_ngram_size`보다 사후 검사로).
  - 품질 비교용으로만 `num_beams=1` 유지(beam은 V100 메모리·시간 비용 대비 이득 작음 [추정]).
- **max_new_tokens 추정** [추정]:
  - 현재 JSON 스키마 기준 문장 1개 ≈ 본문 40–70 토큰 + `{"text":…,"fact_ids":[…],"state":"…"}` 오버헤드 20–35 토큰 ≈ **70–100 토큰/문장**.
  - 섹션 5개 × 3–4문장 = 15–20문장 → 1,100–2,000 토큰 + 섹션 제목·questions·used·omitted 150–300 → **약 1,300–2,300 토큰**. `max_new_tokens=2048`은 경계에 걸림 → 현재 형식이면 **2,560** 권장 + 잘림 감지(`finish_reason`/EOS 미도달) 시 재시도.
  - 슬롯 줄 형식으로 바꾸면 문장당 45–75 토큰 → 15–20문장 ≈ 700–1,500 → `max_new_tokens=1536`이면 충분.
  - 속도 감 [추정]: V100 fp16 HF generate(배치 1, sdpa)로 7B는 대략 15–30 tok/s → 2,000토큰이면 1–2분. 출력 토큰을 줄이는 것이 곧 지연 시간 단축.
- **V100 관련 주의** [추정]: V100은 bf16 미지원·FlashAttention-2 미지원 → `torch_dtype=torch.float16, attn_implementation="sdpa"`. Qwen 계열은 bf16 학습 모델이라 fp16에서 드물게 오버플로(출력이 `!!!!` 반복 등) 보고가 있었음 → 첫 실행 때 짧은 입력으로 확인, 문제 시 `attn_implementation="eager"` 또는 일부 레이어 fp32.

**[심각도: 중간] constrained decoding 권장 여부**
- 결론: **줄 형식으로 바꾸면 불필요**(정규식 + 사후 검증으로 충분). JSON을 유지한다면 **권장**.
- transformers 호환 선택지 [추정, 버전별 API 차이 확인 필요]:
  - **lm-format-enforcer**: `build_transformers_prefix_allowed_tokens_fn(tokenizer, JsonSchemaParser(schema))` → `model.generate(..., prefix_allowed_tokens_fn=fn)`. 설치·적용이 가장 단순.
  - **xgrammar**: `xgr.contrib.hf.LogitsProcessor(compiled_grammar)` 를 `logits_processor=[...]`로 전달. 빠름.
  - **outlines**: `outlines.models.Transformers` 래핑 후 JSON 스키마/pydantic 생성기. 1.x에서 API가 바뀌었으니 고정 버전 사용.
- 스키마 설계 팁: **요청마다 동적 스키마**를 만들어 `slot`(또는 fact_id)을 `enum`=[이번 입력의 ID들]로 제한 → 존재하지 않는 ID 생성이 원천 차단. `state`를 남긴다면 enum 5개. `maxItems`로 문장 수 상한.
- 한계: 제약 디코딩은 **형식**만 보장하고 내용(수치·상태 강도)은 보장 못함. 또 greedy+제약에서 한국어 문장이 짧아지거나 어색해지는 경우가 있음 [추정] → 사후 의미 검사(3절)는 여전히 필요.

### 3-2. FD1 — 숫자를 모델이 아예 쓰지 않게 하는 플레이스홀더 방식

**[심각도: 치명] 규칙 5·8 (FD1·PA1) — 수치 복사를 생성 모델에 맡김**
- 근거 [확인]: "금리 · 금액 · 기간 · 횟수는 Fact 의 값과 단위를 그대로 옮긴다. %와 %p 를 바꾸지 않고, 원 단위를 줄이거나 반올림하지 않는다."
- 의사결정표 [확인]: `기본금리·기본이율·적용이율` "1차 요약의 핵심 숫자로 유지", `최고·최종 공시금리` "'조건 충족 시'라는 표현과 함께".
- 문제 [추정]: 7B는 "10,000,000원"→"1천만 원"(규칙상 허용? 애매), "0.1%p"→"0.1%", "2.50%"→"2.5%" 같은 정규화를 자주 한다. 멘토: "금융은 한두 번 오류도 치명적".
- 설계:
  1. 코드가 fact마다 표시 문자열을 만든다: `F3.val = "연 2.50%(세전, 2026.10.13 기준)"`, `F3.cond = "1,000만 원 이상 예치 시"`.
  2. 모델 입력에는 숫자 대신 토큰만: `F3: 기본금리 = {F3}, 조건 = {F3c}`.
  3. 모델은 `기본금리는 {F3}이며, {F3c} 적용됩니다.` 처럼 **토큰을 그대로 문장에 넣도록** 지시.
  4. 코드 검증: (a) 출력 텍스트에 **아라비아 숫자·%·원·개월이 있으면 실패**(플레이스홀더 밖 숫자 = 환각 또는 복사), (b) 슬롯이 요구한 플레이스홀더가 모두 등장, (c) 없는 플레이스홀더 금지 → 통과 후 치환.
  5. 한글 수사("삼 개월", "천만 원")도 금지 목록에 넣는다.
- 조사 문제: `{F3}이며` 처럼 받침 의존 조사는 치환 후 깨질 수 있음 → 치환 후 `은/는, 이/가, 을/를, (으)로` 자동 보정 함수(마지막 글자 받침 판정, 숫자·%는 읽기 기준 표 사용) 또는 토큰 뒤 조사를 쓰지 않는 문형(「기본금리: {F3}」, 「{F3c}에는 {F3}가 적용됩니다」 대신 「적용 금리 {F3}」) 유도.

## 4. few-shot

**[심각도: 높음] 예시 0개 (zero-shot) + 복잡한 출력 형식**
- 근거 [확인]: 프롬프트에 입력 예시·출력 예시가 없다. 출력 스키마는 `"..."`, `"SATISFIED|UNSATISFIED|…"` 같은 **자리표시 문자열**뿐.
- 위험 [추정]: 7B는 스키마 자리표시를 문자 그대로 복사하는 일이 있다(`"state": "SATISFIED|UNSATISFIED|INFO_MISSING|BANK_CONFIRM_NEEDED|INFO"`). INFO_MISSING의 "조건부 문장 + 질문" 형태, only_in 꼬리표, "입력 기준" 문구는 설명만으로는 일관되게 안 나온다. 한 개의 정답 예시가 규칙 3–4개 분량의 설명보다 효과적.
- 권장: **user/assistant 턴 쌍 1개**를 system 뒤에 넣는다(실제 요청 앞). 조건:
  - 가상의 상품·가상 fact(실제 KB 상품과 key·문구가 겹치지 않게) → 내용 복사 방지. 코드에서 예시 슬롯 ID 형식(`E1…`)이 실제 출력에 나오면 실패 처리.
  - 4–5슬롯으로 짧게(약 300–500 토큰): 정보 1 · 정보 부족 1 · 은행 확인 1 · 예외/only_in 1 · (선택) 미충족 1.
  - 실제 요청과 **완전히 같은 형식**(슬롯 줄 형식 그대로).
- 골격:
```
[user]
상품: 예시저축예금
고객이 알고 싶은 것: 금리가 얼마인지
고객 입력: 예치 예정 {U:amount}

[슬롯]
E1 | 섹션: 금리 | 상태: 정보 | 사용: 기본금리 {A1}, 조건 {A1c}
E2 | 섹션: 금리 | 상태: 정보 부족(마케팅 동의 여부) | 사용: 조건 {A2c} → 우대 {A2}
E3 | 섹션: 해지 | 상태: 정보 | 사용: 중도해지이율 {A3}, 예외 {A3x}
E4 | 섹션: 가입 | 상태: 은행 확인 필요(기존 계좌 보유) | 사용: 제한 {A4}

[assistant]
[E1] 기본금리는 {A1}이며 {A1c} 적용됩니다.
[E2] {A2c}이면 {A2}가 더해집니다.
[E3] 만기 전에 해지하면 {A3}가 적용되며, {A3x}는 이 이율에서 제외됩니다.
[E4] {A4}에 해당하는지는 은행에서 확인해야 합니다.
```
  (상태 고정 문구는 코드가 붙이므로 예시에도 넣지 않는다 — 예시와 실제 처리 방식이 같아야 함.)
- 현재 JSON 형식을 유지한다면 예시도 같은 JSON으로 1쌍, 단 assistant 예시는 2섹션·4문장 이내로.

## 5. Qwen2.5 채팅 템플릿과 system/user 분할

**[심각도: 중간] system 미지정 시 기본 문구** [추정, Qwen2.5 chat_template 기억 — 확인 권장]
- `messages`에 system이 없으면 템플릿이 `You are Qwen, created by Alibaba Cloud. You are a helpful assistant.` 를 자동 삽입. 프롬프트 전체를 user에 넣으면 이 영어 문장이 앞에 붙는다(해는 크지 않지만 "helpful assistant" 성향 → 권유·부연 문장 경향 [추정]). → **system을 반드시 명시**.
- 템플릿은 `<|im_start|>system … <|im_end|>` 구조라 system 길이에 특별한 제한은 없다. 다만 system이 1.5k 토큰 + 입력 수천 토큰이면 출력 규칙이 생성 지점에서 멀어진다.

**[심각도: 중간] 출력 규칙의 위치 — system 끝에만 있음**
- 근거 [확인]: "[출력] JSON 하나만, 다른 글 없이:" 가 system 맨 끝(46–56줄). 실제 입력(user)은 그 뒤에 길게 붙는다.
- 권장 [추정, 소형 모델에서 일반적으로 효과 큼]: user 메시지 **맨 끝**에 3–4줄 리마인더 반복:
```
[다시 확인]
- 슬롯마다 [슬롯ID] 문장 한 줄. 다른 글 없이.
- {…} 토큰은 그대로 쓴다. 숫자를 직접 쓰지 않는다.
- 상태가 "정보 부족"이면 조건부(「○○이면 △△」)로만 쓴다.
```

**system / user 분할 권고안**
- system(고정, 매 요청 동일 → 캐시·버전 관리 쉬움): 역할 1–2줄 + 규칙 6–7개 + 출력 형식. **약 400–600 토큰 목표.**
- (few-shot) user/assistant 1쌍.
- user(요청마다 코드가 조립): 상품·purpose·user_input·슬롯 목록 + 끝에 리마인더.
- system 초안(권장 구조 기준):
```
너는 은행 예금상품 정보를 고객 한 사람에게 맞춘 문장으로 옮기는 모델이다.
판정·선택·순서는 이미 정해져 있다. 너는 각 슬롯을 한 문장으로 쓴다.

규칙
1. 슬롯에 적힌 정보만 쓴다. 슬롯에 없는 사실·일반 상식은 쓰지 않는다.
2. {…} 토큰은 글자 그대로 문장에 넣는다. 숫자·금액·기간을 직접 쓰지 않는다.
3. 조건과 혜택은 한 문장에 함께 쓴다. 다른 슬롯의 조건과 섞지 않는다.
4. 「하나 이상/모두」「그리고/또는」「제외/포함」「이상/초과/이하/미만」의 뜻을 원문대로 유지한다.
5. 상태별: 정보 부족 → 「○○이면 △△」 조건문으로만. 은행 확인 필요 → 무엇을 확인해야 하는지만, 될 것 같다는 말 없이. 미충족 → 모자란 조건을 쓴다.
6. 원문 용어(결산일, 평균잔액, 우대금리 등)를 그대로 쓰고, 상품을 권하거나 비교하지 않는다.

출력: 슬롯마다 한 줄, 「[슬롯ID] 문장」. 다른 글은 쓰지 않는다.
```

## 6. 입력이 길어질 때(앞부분 손실) 대응

**[심각도: 높음] candidate_facts 상한·정렬·필드 규칙 부재**
- 근거 [확인]: 입력 정의에 fact 수 상한·정렬 기준이 없다. candidate_facts 9필드 + judgment_results 4필드가 **별도 배열**이라 모델이 fact_id로 두 배열을 조인해야 한다(소형 모델 약점).
- 의사결정표 [확인]: 프롬프트 IN 항목 21개. 항목당 fact 1–3개면 30–60개 [추정].
- 길이 추정 [추정]: JSON 1 fact ≈ 80–150 토큰(긴 condition/exceptions 원문이면 200+) → 40개면 3.5k–6k + judgment 40×40 ≈ 1.6k → 입력만 5k–8k. 멘토가 지적한 "앞부분 손실" 구간.
- 대응:
  1. **상한**: 한 번 호출당 fact 12–15개(슬롯 10–15개). 넘으면 섹션 단위로 **분할 호출**(섹션별 독립 생성 → 코드가 합침). HF `generate`에 left-padding 배치로 섹션들을 한 번에 돌리면 지연도 크게 늘지 않음 [추정].
  2. **조인 제거**: fact와 판정을 코드가 한 줄로 합침(3-3 슬롯 형식). `state`는 한국어 라벨(정보/적용됨/미충족/정보 부족(필드)/은행 확인 필요)로 — 영어 enum보다 한국어 문장 생성에 바로 이어짐 [추정].
  3. **정렬**: section_order 순 → 섹션 내 중요도 순. 출력 순서와 입력 순서를 일치시키면 모델은 "위에서부터 하나씩" 쓰면 되므로 누락이 줄어든다. must_include 슬롯은 각 섹션 앞쪽.
  4. **필드 축약**: 빈 필드(null/""/[])는 키째 생략. `value/unit/as_of`는 렌더링된 플레이스홀더 하나로 대체. `key`는 짧은 한국어 라벨로. `exceptions` 원문이 길면 2-4 단계에서 요약하지 말고(의미 변형 위험) **원문 그대로 플레이스홀더**로 넘겨 치환 — 모델은 「{F15x}는 제외됩니다」만 쓰면 된다.
  5. **ID 단축**: 긴 fact_id(예: `kb_star_deposit_rate_basic_2026`)를 요청 내 `F1…F15`로 매핑, 출력 후 역매핑. 토큰 절약 + ID 오기 감소.
  6. 리마인더를 user 끝에(5절) — 규칙이 생성 지점 가까이 오게.

## 7. 사후 검증·재시도 파이프라인(요약)

```
build_slots(facts, judgments, deps, must, purpose)   # 선택·배치·의존 폐포·플레이스홀더 렌더 (코드)
→ prompt = system + fewshot + user(slots + reminder)
→ out = generate(do_sample=False, repetition_penalty=1.0, max_new_tokens=1536)
→ parse lines  ^\[(S\d+)\]\s*(.+)$
→ checks per slot:
     - 슬롯 누락/중복/미지 슬롯
     - 필수 플레이스홀더 전부 포함, 미지 플레이스홀더 없음
     - 플레이스홀더 밖 숫자·%·원·한글수사 없음
     - 금칙어(항상/누구나/확실히/보장/추천/유리)  — fact.text에 없을 때
     - 상태 정보 부족 슬롯에 「~이면」 조건형 존재
     - 한자·중국어 문자 [一-鿿] 혼입 없음  (Qwen 한국어 출력의 알려진 혼입 경향 [추정])
→ 실패 슬롯만 재생성(최대 2회) → 그래도 실패: fact.text 원문 + 상태 고정문구로 폴백(표시: "원문")
→ substitute placeholders + 조사 보정 + 상태 문구 + only_in 꼬리표
→ assemble final JSON (used_fact_ids, omitted_must_include, questions_for_user 모두 코드)
→ log: 슬롯별 실패 사유 → 일치율 테스트 지표로 사용
```
